## Image Gallery block mapping — Phase 2: Choose Folder mode + R9 relocation guard (2026-09-09)

Two new `MatrixBuilder` handlers complete the `image_gallery` mapping in `src/config/defaults.php`: `gallerySource` (wire `'images'`/`'folder'` → Craft `imageSource` dropdown's `'images'`/`'folders'`, note the plural) and `assetFolder` (raw ContentiQ folder name → the Craft folder's UID string, what `AssetFolderField` expects). Folder mode requires `assetFolderStrategy: 'sitemap'` — under `'flat'` every page shares one asset folder, so `_handleAssetFolder()` warns and leaves the field `null` rather than writing a folder that would hold every other page's images too.

`MatrixBuilder::_resolveFieldByHandler()` is never given the page's own resolved asset folder path, so `_handleAssetFolder()` reads it from a new `ImageImportService::getPreparedFolderPath()` accessor — the exact string `prepare()` was called with, stashed as a new `$_folderPath` property, deliberately NOT re-derived from `$_folder->path` (which carries a trailing slash in Craft). `AssetFolderPath::withSubfolder()` then appends the gallery's folder name one level under it, and a new `ImageImportService::resolveFolderByPath()` public method (wrapping the existing `_resolveFolderByPath()`, scoped to the run's prepared volume) resolves it to a `VolumeFolder` — same dry-run split as every other folder lookup here (`findFolder()` read-only on dry-run/CP Preview, `ensureFolderByFullPathAndVolume()` only on a real run — this is the exact split the 2026-09-08 fix added, and folder mode reuses it rather than risking a regression with a fresh lookup). A dry-run not-yet-existing folder resolves to `null` silently, no warning — the expected Preview shape. `AssetFolderField` performs no validation of its own (a bad UID normalises to `null` silently), so the resolved folder is also checked against a new `getPreparedVolume()` accessor before its UID is trusted; a mismatch warns and leaves the field `null`.

**R9 — a shared image must not be relocated out of a gallery's folder.** A folder-mode gallery renders by folder membership, not a relation, so an image that's ALSO a hero/card/text-and-media block image on the same page — subtracted from `assets[]` by ContentiQ, imported via the block path into the page folder root — would otherwise be actively relocated OUT of the gallery folder by the existing `'sitemap'` relocation behaviour, silently shrinking the gallery. New `ImportService::_resolveProtectedGalleryFolderIds()` scans the page's `blocks[]` for folder-mode `image_gallery` blocks, resolves each folder name the same way `_handleAssetFolder()` does, and both `importPage()` and `_importCollectionChild()` pass the resulting id set to a new `ImageImportService::setProtectedFolderIds()` call — AFTER `_importPageAssets()` (so a gallery's own `assets[]` have already created its folder) and BEFORE `MatrixBuilder::build()` (so every block image resolved by it honours the protection). `_relocateIfNeeded()` gained one additional early return for an asset whose current folder id is in that set; every other relocation path (legacy root, ordinary ContentiQ-folder sub-level moves) is unchanged. The set resets to empty on every `prepare()` call (once per page) so one page's protection can never leak into the next page's own `assets[]` filing step. Two documented, accepted residual limits: no-op under `'flat'` (folder mode doesn't resolve there either), and per-page only (an asset physically sitting in ANOTHER page's gallery folder is still relocated when that other page syncs — rare post-1.25.0 self-heal, but not closed).

`docs/assets.md` gained a full "Image Gallery 'Choose Folder' mode" section (the two handlers, the dry-run split, the volume check) plus an "R9 — protecting a shared image from sitemap relocation" subsection (the trap, the fix, the two residual limits) — both new sections, not folded into existing ones, since folder mode is genuinely new behaviour rather than a variant of something already documented. The "Multi-image blocks" section got one clause added: folder mode's `images[]` is always `[]` on the wire, and the handler still correctly emits the empty array rather than omitting the key.

Test coverage: `tests/run-transforms.php`'s "MatrixBuilder — image_gallery block mapping" section (renamed from "…(Phase 1)") gained folder-mode, flat-guard, dry-run, and wrong-volume cases alongside the existing images-mode one — all via full `build()` calls against a fake `images` double exposing the three new accessor/resolver methods. A new "ImportService — R9 protected-folder-set" section exercises `_resolveProtectedGalleryFolderIds()` directly via Reflection (flat no-op, non-gallery/images-mode blocks ignored, folder-mode resolution, de-duplication across two galleries sharing a folder, an unresolvable folder contributing nothing). Needed one small test-infra fix, not a new stub: `AssetFolderPath::withSubfolder()`'s default (non-injected) sanitizer calls `craft\helpers\Assets::prepareAssetName()`, and the existing `tests/fixtures/assets-helper-stub.php` for it was loaded lazily mid-file (`require`, not `require_once`) — now `require_once` at both the earlier (image_gallery) and later (per-item folder override) load sites so both can use it safely. `tests/run-transforms.php` now 209 assertions (was 189), `tests/run-security.php` untouched at 47, both green; `php -l` clean on every changed PHP file. ## Collection-child Body Text content — `blocks[]` + optional `content` together (2026-09-07)

ContentiQ's export contract for collection children is changing: a page with ranges marked up can now carry `blocks[]` PLUS an optional `content` key holding the page's explicitly-marked **Body Text** sections — a MANUAL markup block the editor applies deliberately (not leftover/unmarked text), merged in page order, present only when the editor marked at least one Body Text range (omitted entirely when they marked none). Previously the wire contract was strictly either/or, and `_buildCollectionChildContentFields()` always cleared `contentField`/`headingField` to `''` whenever `blocks[]` was present, discarding any content outright.

**Same-day amendment:** the wire shape is unchanged from the first cut of this entry (`blocks[]` + optional `content`, rendered into the mapped `contentField`), but the semantics flipped — the earlier revision described `content` as "leftover (unmarked)" text ContentiQ swept up automatically; it's now editor-marked Body Text, so the code comments/docblocks and the warning wording below were reworded to match, and the internal variable was renamed accordingly. Also new: `horizontalRule` nodes are ContentiQ layout aides and must NEVER reach the CMS — `NodesRenderer::renderDocument()` (the raw-ProseMirror collection-child path) now skips them defensively (renders `''`, not `<hr>`), belt-and-braces since the app now strips them at export but this also covers older app payloads and legacy full-content syncs. `NodesRenderer::render()` (the block-serialised path) was already skipping them — no `'horizontalRule'` arm exists there, so it already fell through to `default => ''` — left untouched, now with an explicit regression test.

`_buildCollectionChildContentFields()` (`src/services/ImportService.php:2710`) still branches on whether that Body Text `content` is non-empty: `headingField` is always explicitly cleared to `''` when blocks own the page (blocks own the heading — `extractHeading()` never runs on this path); `contentField` renders the Body Text doc wholesale via `NodesRenderer::renderDocument()` when non-empty, otherwise it's cleared to `''` exactly as before — which also keeps behaviour byte-identical against older ContentiQ deployments that still send `blocks[]` with no `content` key at all. `_importCollectionChild()` computes `$hasBodyTextContent` once (`!empty($blocks) && !empty($content)`, renamed from `$hasLeftoverContent`) and passes it through to both the field-value build and the guard-2 warning builder.

`_buildBlockOwnershipWarnings()`'s parameter is now `$contentReplacedWithBodyText` (renamed from `$contentReplacedWithLeftover`) — the contentField warning now reads "…replacing previously non-empty '{field}' field with Body Text content." when Body Text is being written, vs. the existing "…clearing previously non-empty '{field}' field." when it's genuinely cleared. `headingField`/matrix warnings are unaffected.

Docs updated in the same change: `docs/import-pipeline.md` ("Content-type routing for collection children" — the wire-contract paragraph reworded to Body Text semantics, plus a `horizontalRule` note) and `docs/integration.md` (export envelope paragraph reworded the same way).

`php -l` clean on `src/services/ImportService.php`, `src/services/NodesRenderer.php`, and `tests/run-transforms.php`. `_buildCollectionChildContentFields()` and `_buildBlockOwnershipWarnings()` are both pure and already covered via the existing Reflection + craft-stubs harness — the warning-wording assertions updated to the new "Body Text content" copy. `NodesRenderer::renderDocument()`'s `horizontalRule` skip and `render()`'s pre-existing (unchanged) skip both got new direct coverage. `tests/run-transforms.php` now 150 assertions (was 147), all passing; `tests/run-security.php` untouched at 47. Not released — no version bump, no tag.

## Route CTA blocks by ContentiQ `fields.source` — page vs. global footer CTA (2026-09-04)

Every `call_to_action` block now carries `fields.source` (`'page'` or `'global'`, absent ⇒ `'global'` — ContentiQ's own default, mirrored verbatim rather than re-decided), and the importer routes on it instead of always creating an inline per-page block.

**`'page'`** — the per-block handling (entry creation/update, inline Matrix block, `contentiq_cta_syncs`) is byte-identical to the pre-existing behaviour: unchanged. It now also contributes to the page-level lightswitch decision below (purely additive — the new OFF rule).

**`'global'`** — no inline `callToAction` Matrix block, no `contentiq_cta_syncs` row (that table means per-page ownership, which doesn't apply to a shared entry). Instead, gated on the same `contentiq_globals_sync` consent lock `GlobalsImportService`/`SyncJob` use, the single SHARED `callToActionEntry` is created/updated and related on `globalContent.globalChooseCallToAction`. Two `'global'`-labelled CTA blocks in one run resolve to **one** entry — the relation is read fresh before each write, so the last-processed block's content wins; no special-casing needed, it falls out of always reading the current relation rather than caching it. Globals locked (the default outside an unlocked `SyncJob` run — CP upload/CLI/widget essentially always see it locked, matching the existing "globals never travel via upload" posture) skips both site-wide writes and warns, but the page's own lightswitch decision (below) is still applied (page-scoped, already consented via the page's own unlock).

**The `footerCallToAction.showGlobalCallToAction` lightswitch is one aggregate decision per page**, made once every CTA block has been classified — not a property of any single block: **ON** when ≥1 block routed `'global'` (wins even alongside `'page'`-source ones); **OFF** — the rule this amendment adds — when the page carried ≥1 `'page'`-source block and none `'global'` (the page supplies its own CTA, so the shared footer one is disabled, since it would otherwise duplicate); **untouched** when there were no CTA blocks at all (absent payload data never deletes). `_buildFooterGlobalCtaField()` writes the resolved value (read-modify-write — every sibling field, notably `callToActionLayout`, is left untouched, for free, because `craft\fields\ContentBlock`'s own save path only overwrites handles present in the `'fields'` array passed to it). Both routing notes go to a NEW, report-only `routingNotes` result key — **never** `blockNotes` and never `warnings`: `'Call to Action → global footer CTA'` per `'global'`-source block resolved, `'Page CTA → global footer CTA disabled'` once when the decision lands OFF. (Corrected same-day: an earlier version of this change appended these messages to `blockNotes`, which `SyncJob`'s post-import auto-lock step and `CpController::actionWidgetSync()` both persist verbatim into `contentiq_entry_syncs.notes` — the column the sidebar widget displays as "ContentIQ Notes." That field must contain only real notes transmitted in the payload, never plugin-generated text, so routing messages now live in `routingNotes`, which nothing persists — it exists only in the run's result JSON.) Routing is expected behaviour, not an actionable problem, and `warnings` is reserved for genuine problems — it drives run/page status (any non-empty `warnings` flips the run to `warnings`), and since absent `fields.source` defaults to `'global'`, pushing the ON note into `warnings` would have stamped nearly every legacy sync as warning-laden. `result.twig` and `sync-result.twig` both render `blockNotes` and `routingNotes` as neutral info lines on each page's row (muted styling, no effect on warning counts/status), so the routing is still visible on every screen even though it never touches the persisted notes column.

Defensively guards the `UnknownPropertyException` trap `_buildHeroInnerFields()`'s `heroStyle` check already exists for: an unrecognised handle inside a `ContentBlock`'s nested `'fields'` array throws, uncaught by Craft's own save path (only `InvalidFieldException` is caught). `_buildFooterGlobalCtaField()` probes both the outer `footerCallToAction` field and its own nested field layout's `showGlobalCallToAction` handle before writing either — either miss skips the write, never a crash, but whether it also warns is now asymmetric on the decision it's serving: ON + a missing field still warns (unchanged — content that should route to the footer silently can't); OFF + a missing field is silent — there's nothing to disable, and collection children (case studies/team) routinely carry `'page'`-source CTA blocks with no footer field at all, so warning on every one of them would be spam, not signal.

Refactored rather than duplicated: `_resolveCtaEntry()`'s title extraction and content-field mapping (richText/image/desktopBackgroundImage/actionButtons) are now `_extractCtaTitle()`/`_buildCtaContentValues()`, shared with the new global path — `_resolveCtaEntry()`'s own behaviour for `'page'` blocks is unchanged (confirmed by re-reading it end to end after the extraction). The per-block routing loop itself (walk `matrixData`, dispatch each `_cta`-flagged placeholder) was already duplicated between `importPage()` and `_buildBlockFieldValues()` (collection children carrying `blocks[]`) before this change; both now call one shared `_resolveCtaBlocks()`, so every one of the four entry points (CLI, CP upload, `SyncJob`, sidebar widget — all funnel through `importPage()`) routes identically without a fifth place to keep in sync. Confirmed via grep that no other code path touches `callToActionEntry`/`callsToAction`/`chooseCallToAction` outside `ImportService`/`MatrixBuilder` (which only emits the placeholder, never writes).

New overridable config keys (`_getConfig()`'s defaults array, same pattern as `matrixField`/`seoField`): `footerCtaField`, `footerCtaShowGlobalField`, `globalContentSet`, `globalChooseCtaField` — all default to the Craft Starter's own handles, verified against `craft-starter/config/project/fields/footerCallToAction--*.yaml` and `globalSets/globalContent--*.yaml`.

`preserveBlockIdentity` interaction: a `'global'`-routed block's placeholder is removed from both `$matrixData` and `$blockKeyConsumption` together (same key, same pass) so `_recordBlockSyncMap()`'s zip against the saved Matrix field's actual order stays aligned — reasoned through, not live-tested (the flag has no integration coverage regardless, per existing doctrine).

Docs updated in the same change: `docs/block-mapping.md` ("CTA entry creation" gained a "Source routing" subsection — the durable home for the mechanics), `docs/import-pipeline.md` (new "CTA source routing" pointer section, plus the step-10/`contentiq_cta_syncs` mentions updated), `docs/globals.md` (new note under "Mental model" and a "Consent model" bullet covering the second consumer of the same lock).

`php -l` clean on all changed files. `_ctaSource()` (the pure page/global classifier) and `_buildFooterGlobalCtaField()`'s field-layout guard (missing outer field / not-a-ContentBlock / missing inner handle / both-present, now crossed with both `$showGlobal` intents to cover the ON-warns/OFF-silent asymmetry) are covered in `tests/run-transforms.php` via the same Reflection + craft-stubs approach the hero-shape probe already uses — `_buildFooterGlobalCtaField()` now takes `$config` as a parameter (matching `_resolveSeoFields()`'s convention) instead of calling `_getConfig()` itself, specifically so it stays testable without a `Craft::$app` bootstrap. `_resolveCtaBlocks()`'s own tri-state return (`?bool`) is directly asserted for its two Craft-free early-return-null ("untouched") paths — dry run, no CTA blocks at all; the ON/OFF legs themselves still need a live `Entry`/`GlobalSet`, same gap `_resolveCtaEntry()`/`_resolveGlobalCtaEntry()`/`SyncJob` already have. `tests/run-transforms.php` (139 assertions, was 129) and `tests/run-security.php` (47 assertions) both pass. Not released — no version bump, no tag.

## Fix unlock-consent no-op for never-synced entries + sync-result rendering (2026-09-04)

Two independent bugs.

**Unlock consent silently no-op'd for never-synced entries.** `SyncJob::_applyLockState()`'s unlock branch was UPDATE-only: for an entry with no `contentiq_entry_syncs` row yet — the Craft homepage Single is the standing example, since it pre-exists so `findExistingEntry()` matches it, but a row is only ever created by the post-import auto-lock step — the UPDATE matched zero rows, nothing was inserted, and the per-page lock check (missing row ⇒ locked) then skipped the entry with "Skipped — entry is locked." even though the user had explicitly ticked its unlock checkbox on the Sync screen. Chicken-and-egg: unlocking needed a row, the row needed a successful import, the import needed the unlock. `_applyLockState()` now upserts per id — update if a row exists, otherwise insert one with `locked => false` (auto-lock fills `synced_at`/`notes`/`contentiq_page_id` after a successful write, same as it always has). IDs are sanitised before use (cast to positive int, deduped, filtered to `\craft\elements\Entry::find()->id($ids)->status(null)->ids()`) since `$unlockIds` arrives from a POST body — junk input can no longer create an orphan sync row. Grepped the whole repo for other UPDATE-only writes to `contentiq_entry_syncs` implementing the same "apply the user's unlock consent" semantics: `CpController::actionToggleLock()` (the sidebar widget's per-entry toggle) already upserts and needed no change; `actionClearNotes()` is UPDATE-only but only clears notes, not lock state, so left alone; the console `ImportController` only ever reads locks (`--force` bypasses the check entirely, never writes unlock consent) and has no unlock write path at all. `_applyLockState()` was the only offender.

**Import-history result screen rendered sync runs as garbage.** Since the 1.22.0 sync overhaul, `SyncJob` stores `contentiq_import_runs.result` as a shape-tagged object (`{pages, globals, ackWarning}`), while upload/CLI/widget runs still store the old flat per-page array. The legacy `actionResult()`/`_cp/result.twig` pair (still used by those other run types) iterated `run.result` directly, so a `sync`-type run landing there rendered three `? | Failed | 0 | 0` rows — one per top-level key — instead of the actual pages. `actionResult()` now redirects (302) a `sync`-type run straight to `contentiq-importer/sync/result/<id>`, the purpose-built screen that already handles the wrapped shape. `result.twig` also gained the same `pages = run.result.pages is defined ? run.result.pages : run.result` unwrap `sync-result.twig` already had, as a belt-and-braces fallback for any other path that ends up rendering a wrapped result. `history.twig`'s "View" link now points `sync`-type rows straight at the sync result route rather than relying on the controller redirect.

Docs updated in the same change: `docs/import-pipeline.md` ("SyncJob's passes" step 1, "Lock semantics") and `docs/cp-and-widget.md` (History/Result bullets) now describe the upsert and the redirect/fallback.

No behaviour change for `$unlockIds === null` (no lock changes at all) or the blanket re-lock of every synced row not in `$unlockIds` — both untouched. `tests/run-transforms.php` and `tests/run-security.php` still pass (116 + 47 assertions); neither covers `SyncJob` (it needs `Craft::$app->getDb()` and a live `contentiq_entry_syncs` table/`Entry` model, outside this repo's pure-PHP/Craft-free test style — see "Testing" in `AGENTS.md`), so no automated case was added for the upsert path. Not released — no version bump, no tag.

## Fix collection-child CTA crash — "Too few arguments" (2026-08-24) — 1.21.1

`_buildBlockFieldValues()`'s CTA loop still called `_resolveCtaEntry()` with the pre-1.16.0 3-argument shape, while the signature requires 5 (`$pageId`, `&$claimedElementIds` — the stable `(page_id, block_id)` identity contract). The page path was updated when the signature changed; the collection-child path came in on the other side of merge `dff3195` and never was. Result: any real (non-dry-run) sync of a collection child whose `blocks[]` contains a `call_to_action` block threw `ArgumentCountError` — surfaced on Lucia 2026-08-24, latent since 1.17.0. Fix derives `$pageId` from `$data['document']['id']` (same as `importPage()`) and a per-child claim set inside `_buildBlockFieldValues()`, so collection-child CTAs now also get stable identity in `contentiq_cta_syncs` instead of title-only matching.

## Read-only export acknowledgement + full-project Sync tree (2026-08-21)

ContentiQ's export GETs (`/api/v1/export`, `/api/v1/pages/{slug}/export`) are becoming side-effect-free — they no longer flip page statuses just by being fetched. The CMS now explicitly acknowledges pages it actually wrote, and the Sync screen shows ContentiQ's full project tree (not just what's already been imported) on load.

**Acknowledgement (`POST /api/v1/pages/ack`):**
- `ContentIQApiService::ackPages(int[] $pageIds)` — Bearer-authed POST with `{"page_ids": [...]}`, 15s timeout. Empty input is a no-op (no request). Any failure (unconfigured API, network error, non-2xx, malformed JSON) is reported via `success`/`error` but never throws — always non-fatal to the caller.
- `SyncJob` collects the ContentiQ page id of every page result that actually wrote this run (`success`, not `skippedLocked`, not ImportService's own non-fatal `skipped`, has an `entryId`, carries a `contentiqPageId`) and makes ONE batch ack call after PASS 2 (card refs). A failure appends a warning to the run result (`result.ackWarning`, new sibling of `pages`/`globals`) and flips the run status to `warnings` — rendered as a small banner on the sync report screen. Never fails the sync.
- The sidebar widget sync (`CpController::actionWidgetSync()`) acks its single page the same way after a successful sync, non-fatally logged on failure.
- `ContentIQApiService::fetchExport()` gained optional `$timeout`/`$connectTimeout` overrides (defaults unchanged: 120s/10s) — used by the Sync screen (see below) for page-load responsiveness without touching the queue job's call.

**Full-project Sync tree:**
- `CpController::actionSync()` now calls `fetchExport()` (20s/5s timeouts) on every page load and builds the FULL ContentiQ project tree via new `_buildFullSyncTree()`, rather than only listing entries already in `contentiq_entry_syncs`.
- Each export page is matched to Craft via `ImportService::findExistingEntry()` — the same id-first resolver SyncJob's own lock check uses, so the screen and an actual sync always agree on what a page maps to. A match carries its lock state (missing sync row ⇒ locked, same default as SyncJob); no match renders a "New" row (never locked — SyncJob's lock check only runs when `findExistingEntry()` finds something, so an unimported page always imports regardless of any selection — matches first-sync-ever behaviour, unchanged).
- Pages-group hierarchy is built from the export's own `document.parent_slug`/`slug` (the only source that can link a not-yet-imported child to its parent — a new page has no Craft structure position yet). Collection-entry rows stay flat (parentSlug forced null), matching the pre-existing local-only view and avoiding a latent bug in the shared tree macro (a parentSlug pointing outside its own group silently drops the row — pre-existing, not touched).
- An unmapped `content_type` (no `content_types` route) is skipped from the tree entirely, mirroring `ImportService::_importCollectionChild()`'s own non-fatal import-time skip.
- Old behaviour — building the tree from `contentiq_entry_syncs` only — is preserved verbatim as `_buildLocalOnlySyncTree()`, now the fallback whenever the API is unconfigured or unreachable (previously unconfigured hard-redirected away from the screen entirely; it now renders the local-only view with a dismissible warning banner instead — the screen never 500s because ContentiQ is down).
- `sync.twig`: "New" rows get a blue "New" status badge (checkbox default-checked, but — since it has no lock row to toggle — the status cell and the `unlockIds` payload both ignore its checked state; a hint line spells this out). Existing lock-toggle/select-all/select-none behaviour for already-imported rows is unchanged.

**Real opt-out for "New" rows:** the above shipped New rows as checked-but-disabled — SyncJob always imported them regardless of the checkbox. Ben tested it and wanted a genuine skip. New checkboxes are now enabled (still checked by default) and carry `data-contentiq-page-id` (the export's `document.id`); unchecking one flips its status cell to "New — skipped" (gray, still toggleable) and the checkbox now participates normally in shift-click / Select All / Select None / the summary counter (the `disabled`-skip guards for New rows are gone).

- **`sync.twig`** — submit handler collects `excludeNewIds`: ContentiQ page ids of unchecked New rows, appended to the FormData as a JSON array alongside `unlockIds`. Deliberately opt-out semantics: if JS breaks or an id is missing, nothing is excluded and the page imports as before — never silently skip by default. Hint copy updated: unchecking a New page skips it for this sync only; it reappears as New next time.
- **`CpController::actionRunSync()`** — reads `excludeNewIds` the same tolerant way as `unlockIds` (`Json::decodeIfJson`, non-array/malformed → `[]`, never `null`), passes it to `SyncJob`.

## Blockquote node type support (2026-08-20)

`NodesRenderer` no longer silently drops `blockquote` nodes — both rich-text consumption paths now render them (previously both `match` statements fell through to `default => ''`).

- **`_renderNode()` (flat `nodes[]` blocks path)** — new `'blockquote'` arm calling `_renderBlockquote()`. Mirrors `_renderParagraph()`'s idiom exactly: prefers inline `content` (marks, hardBreaks) via `_renderInlineContent()`, falls back to `htmlspecialchars($node['text'])`. Emits `<blockquote><p>…</p></blockquote>` — CKEditor's Block Quote feature expects a paragraph inside the blockquote. Empty blockquote → `''`.
- **`_renderDocNode()` (raw ProseMirror `content` path, collection children)** — new `'blockquote'` arm calling `_renderDocBlockquote()`. Here the shape is the NESTED ProseMirror form (`{type:'blockquote', content:[block nodes]}`, not flat text) — wraps `<blockquote>` around each child block rendered through the existing `_renderDocNode` recursion, so nested paragraphs/lists inside the quote keep their own markup. Empty → `''`.
- The two paths take genuinely different input shapes for the same node-type name and are handled separately, same as `paragraph` already is in each.
- `CLAUDE.md` and `PLUGIN-SPEC.md`'s NodesRenderer node-type tables updated with the new rows.
- Test coverage added to `tests/run-transforms.php`: flat text-only, flat with `content` (hardBreak + mark), flat empty, nested single paragraph, nested two paragraphs, nested empty.
